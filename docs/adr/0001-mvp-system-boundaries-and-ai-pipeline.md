# ADR-0001: MVP 시스템 경계와 AI 응답 파이프라인

- Status: Accepted
- Date: 2026-10-04
- Owners: Product, Engineering
- Related: [BARO PRD](../PRD.md)

## 맥락

BARO는 사용자의 법률 문제를 구조화하고, 확인할 쟁점과 준비할 자료 및 일반적인
다음 절차를 안내하는 제품이다. 결과가 법률 판단으로 오인되거나, 출처가 확인되지
않은 내용과 사용자가 제공하지 않은 사실이 섞이면 제품의 핵심 신뢰가 훼손된다.

동시에 현재 저장소는 구현이 시작되지 않은 상태다. MVP 단계에서 여러 서비스를
미리 분리하면 배포와 관측, 정책 변경, end-to-end 검증의 비용이 커진다. 반대로
모든 로직을 하나의 AI 프롬프트에 넣으면 정책 적용 여부를 검증하기 어렵고, 모델이나
법률정보 공급원을 교체할 때 변경 범위가 커진다.

따라서 첫 구현 전에 배포 단위와 내부 모듈의 책임, 그리고 사용자 입력이 최종
응답으로 바뀌는 경로를 결정할 필요가 있다.

## 결정

### 1. MVP는 모듈형 모놀리스로 구현한다

MVP의 서버 기능은 하나의 배포 단위로 시작한다. 다만 코드 안에서는 다음 책임을
명시적인 모듈 경계로 분리한다.

- `intake`: 사건 입력, 추가 질문, 사용자 응답 수집
- `case-structure`: 사건 요약, 타임라인, 관계와 미확인 정보 구조화
- `legal-retrieval`: 법령 및 공식기관 자료 검색과 원문 메타데이터 관리
- `guidance`: 쟁점, 증거 체크리스트, 일반 절차 생성
- `policy`: 지원 범위, 긴급 상황, 금지·제한 출력 판정
- `citation`: 생성 결과의 주장과 출처 연결 및 검증
- `llm-gateway`: 모델 호출, 구조화 출력, 재시도, 사용량과 오류 기록
- `response`: 검증된 결과와 고지 문구를 사용자 응답으로 조립

모듈은 서로의 내부 저장소나 모델 SDK를 직접 사용하지 않고 공개된 애플리케이션
인터페이스를 통해서만 통신한다. 외부 모델 호출은 모두 `llm-gateway`를 거친다.

초기에는 네트워크 서비스로 나누지 않는다. 독립적인 확장, 보안 격리 또는 장애
격리가 실제로 필요해질 때 별도 ADR을 통해 서비스 분리를 결정한다.

### 2. AI 응답은 단계가 분리된 파이프라인에서만 생성한다

사용자에게 보이는 주요 결과는 다음 경로를 거친다.

```text
사용자 입력
  -> 입력 정규화 및 민감정보 처리
  -> 지원 범위 및 긴급성 판정
  -> 사건 구조화 / 추가 질문 결정
  -> 공식 자료 검색
  -> 근거에 제한된 구조화 결과 생성
  -> 법률 안전 정책 검사
  -> 인용과 근거 검사
  -> 응답 조립 및 AI 고지
  -> 사용자 응답
```

한 번의 모델 호출이 검색, 법률 판단, 인용 생성, 안전 검사를 모두 담당하지 않게
한다. 각 단계는 입력과 출력을 스키마로 정의하고 독립적으로 테스트할 수 있어야
한다.

### 3. 파이프라인은 다음 불변조건을 지킨다

- 지원 법역과 기준일이 확정되지 않은 법률정보를 확정적으로 표시하지 않는다.
- 검증되지 않은 법령, 판례 또는 공식기관 링크를 출처로 표시하지 않는다.
- 사용자가 제공한 사실, 검색된 사실, AI가 정리하거나 추론한 내용을 구분한다.
- 사용자가 제공하지 않은 날짜, 행위, 의도 또는 증거를 사건 사실로 추가하지 않는다.
- 외부 모델로 전송 가능한 데이터는 개인정보 정책이 허용한 형태로 제한한다.
- 긴급하거나 지원 범위를 벗어난 사건은 일반 생성 흐름보다 정책 결과를 우선한다.
- 안전 또는 인용 검사가 실패하면 해당 내용을 제외하거나 확인 불가 상태로
  응답한다. 검증 전 결과를 그대로 통과시키지 않는다.

### 4. 프레임워크와 공급자는 이 ADR에서 결정하지 않는다

웹 프레임워크, 데이터베이스, 검색 엔진, 모델 공급자, 배포 플랫폼은 위 경계를
지킬 수 있어야 하지만 이 ADR의 결정 대상은 아니다. 해당 선택은 요구사항과
운영 제약을 확인한 후 별도 ADR에서 기록한다.

## 고려한 대안

### 단일 프롬프트 중심 구조

가장 빠르게 시제품을 만들 수 있지만 검색 근거, 사실 추가, 금지 출력과 같은 실패의
원인을 분리하기 어렵다. 회귀 테스트와 정책 감사도 취약하므로 채택하지 않았다.

### 처음부터 마이크로서비스로 분리

각 책임을 강하게 격리할 수 있지만 MVP의 배포, 로컬 개발, 관측 및 스키마 변경
비용이 과도하다. 현재 트래픽과 조직 규모로 정당화되지 않아 채택하지 않았다.

### 외부 법률 AI API에 전체 기능 위임

초기 개발량은 줄지만 출처 검증, 개인정보 처리, 출력 정책과 장애 대응을 BARO가
통제하기 어렵다. 특정 공급자 종속도 커지므로 핵심 파이프라인으로 채택하지 않았다.

## 결과

### 긍정적 결과

- 한 배포 단위로 빠르게 MVP를 만들면서도 책임별 테스트가 가능하다.
- 모델과 검색 공급자를 교체하더라도 제품 정책 모듈을 유지할 수 있다.
- 응답이 어느 단계와 근거에서 만들어졌는지 추적하기 쉬워진다.
- 안전 검사와 인용 검사를 제품 기능과 독립적으로 강화할 수 있다.

### 비용과 제약

- 단일 모델 호출 방식보다 구현 코드와 지연 시간이 늘어난다.
- 모듈 간 스키마 버전과 파이프라인 상태를 관리해야 한다.
- 모놀리스 내부 경계를 지키기 위한 의존성 검사와 코드 리뷰 규칙이 필요하다.
- 검증 실패 시 답변 범위가 줄어들 수 있으며 이를 정상적인 제품 동작으로 설계해야
  한다.
